# 14-15 Nov night: picture-first reading, answers from the reading, models on Modal

What was decided, built and measured, and what is left. Data problems are in `docs/DATASET_ISSUES.md`.
Branch `picture-first-qa`; trained models on the GitHub release `v0.1-models` (`python tools/get_models.py`).

## Decisions the user made (follow them)

1. **Answers report what people see on the drawing**, never what a file stores invisibly (duplicate DXF elements are
   counted once; legend sample symbols are not counted; the answer does not talk about hidden copies).
2. **Picture first.** Every input becomes a page picture; the picture is read ONCE into a structured reading (the
   "layer"); **questions are answered only from that reading, never from the image.** If something was not read, the
   answer says what is missing; the fix is to read again, not to let the answer model look at the picture.
3. **Every question about a drawing goes straight to the answer agent** (Kimi now). The rule-based engine misread
   near-miss questions with confidence (see below); it is kept for building models (IFC) only.
4. **Answer model: Kimi K3.1 Pro** on our Modal endpoint for now, **Claude later** (when the Anthropic API key is given).
5. **Reading step at medium effort** (Opus, headless Claude Code). Test and comparison agents run at low effort.
6. **Our trained models run on Modal**, not on the Mac.
7. No splitting one sheet's reading over many agents (single agent per sheet).

## Architecture now

```
upload (demo/app.html, /app)
  -> drawqa/layer.py  ingest(file)                         once per file, cached and versioned (LAYER_VERSION)
       page picture: image as is | PDF page rendered | DXF/DWG drawn by drawqa/cad.py | IFC: no picture
       our trained models (drawqa/convert.py), on Modal by default (drawqa/remote.py -> app drawqa-infer):
         detector (doors, windows, fixtures), wall/room model (sheets <= 4000 px only), OCR / PDF text, scale,
         legend symbols removed
       Claude (Opus, medium, `claude -p` headless, brief tools/discover/brief_discover_model.md, tools ptool.py):
         checks the models' doubtful items, finds every other kind of thing, outlines rooms on big sheets
       -> layer.json: classes of items with ids ("door#3"), texts, scale, notes
  -> drawqa/ask.py  ask(file, question)
       answer agent (drawqa/llm.py: Kimi; Qwen and Claude Haiku selectable) with tools over the layer only:
         items(cls), find_text(q), python(code) in a sandbox (no network, no writes); must finish with
         answer(value, unit, tier, evidence ids, explanation)
       checks in code: evidence ids must exist, else "detected"/"measured" is downgraded to "estimated"
       building models (IFC): the engine (drawqa/solve.py)
```
Tiers: read (printed) / measured (geometry at a known scale) / detected (counted items) / estimated (rests on an
assumption) / cannot determine (with the reason).

## Run it
- `.venv/bin/python -u demo/server.py` -> http://localhost:8000/app (old page at `/`). The server warms Kimi and the
  model service at start. Drop a file, watch the reading steps, ask; evidence is highlighted on the drawing.
- Model service: `.venv/bin/modal deploy tools/modal_infer.py` (redeploy after changing drawqa code that runs there:
  detect.py, segment.py, ocr.py, textlayer.py, or the weights). `DRAWQA_INFER=local` runs the models on this machine.
- Settings: `DRAWQA_DISCOVER_EFFORT` (medium), `DRAWQA_DISCOVER_TIMEOUT` (600 s), `DRAWQA_ANSWER_LLM` (kimi|qwen),
  `DRAWQA_USE_ENGINE=1` (old engine routing, for comparison), `DRAWQA_SEG_MAX_SIDE` (4000).
- Kimi key: `~/.config/drawqa/modal_endpoint_auth` (never in git). Claude steps use the local Claude Code login.

## What was measured

### Doors and windows: our detector is already at the ceiling (fine-tuning on Opus labels is not worth it)
| held-out test | detector alone | Opus alone | detector + Opus |
|---|---|---|---|
| CubiCasa, 5 plans, 104 doors+windows (human key) | 104, 1 extra | 92, 13 extra | 104, 1 extra |
| Swiss, 6 plans, 239 doors+windows (key from the DXF via tools/swiss_labels.py) | 239, 1 extra (legend sample) | - | - |
Opus alone boxes doors on the swing inside the room, not the opening (8 of its 11 "misses" on plan 1000), and misses
some. The detector was trained on CubiCasa (preview excluded), Swiss plans of other sites (65 preview plans excluded,
split by site) and BIM exports; FloorPlanCAD (f26l) was tried and rejected. So the Swiss test is "unseen buildings,
seen style". On the whole 65-plan Swiss set, the picture route (PDF only) scores doors 126/130, windows 118/130.

### Opus effort for the reading (plan 729, 48 dataset objects, same start)
| effort | found | time | cost |
|---|---|---|---|
| default | 43 | 6.0 min | $1.75 |
| medium | 37-39 | 2.2 min | $0.73 |
| low | 33-35 | 1.1 min | $0.48 |
About 90% of an agent's time is writing (thinking + code), not tools. Low + 12-call cap: no faster. Low + bulk symbol
tool (`ptool auto`): worse (junk hits on plain rectangles). Sonnet low: fastest ($0.24, 40 s), finds least.
Dense sheets lose more at low (data centre: 17 rack rows instead of 204 racks) until the brief says "count each unit".

### The rule engine misreads near-miss questions (why every question now goes to the agent)
"How many wardrobe units?" -> read as storage rooms -> 0 "detected" (the reading has 11 wardrobe cells).
"How many apartments?" on a Swiss picture -> 0 "measured" (apartment outlines exist only in DXF; Whg. A-D are printed).
"What is the scale and plan number?" -> "35.8 mm per pixel" (the sheet prints 1:200 (A3), 2082-9385).
Also: engine counts came from the raw detector, so Opus's removals (a doorway with no door; 2 false "windows" on pipe
crossings) were ignored. Kimi from the reading: 7 doors, 0 windows, 4 apartments, "1:200 (A3); plan 2082-9385".

### Our models on Modal (app drawqa-infer, L4 GPU + 8 CPUs)
Same detections as local (plan 41: 60/60 boxes, confidences within 0.001). UK school sheet (14,000 x 9,902 px): 81 s
(detector 19.5, outlines 9.3, OCR 51.6) instead of 269 s on the Mac CPU. Cold start about 70 s (warm it).

### Reading times (Opus low, normal sheets): 1.5-2.5 min, about $0.50-0.80 each; the dorm sheet at low: 107 s, $0.78.

## Known problems (fix next)
1. **Big dense sheets are under-read by one agent:** on the dorm sheet the reading found 12 kinds (the earlier
   multi-agent dorm pipeline found 33 kinds / 1,100 items); common areas, laundry, gym equipment are missing.
2. **No walls on big sheets:** the wall model is off there. Next: run it in native-resolution tiles like the detector
   (dorm walls are about 10 px thick, like the training scans) and merge.
3. **Windows missed on big sheets:** above 30 tiles the detector looks in one orientation only (its thresholds were
   tuned on four). On the GPU, four orientations are affordable: raise `DRAWQA_TTA_MAX_TILES` in the Modal service.
4. OCR is the slowest Modal step (tiles in sequence): run tiles in parallel on the 8 cores.
5. The reading step runs Claude Code with shell access, not sandboxed: sandbox it (as the Kimi harness did) before
   anyone else uploads files.
6. The reading step uses the local Claude Code login: subject to the plan's usage limits; switch to the API key.
7. Scale: read the printed "1:N" (Swiss) and grid dimensions (data centre); door-only estimates can be 20-27% off.
8. Code checks for "cannot determine": scale prerequisite, a missed-answer check (the reading has a matching class or
   text), unanswerable properties (heights, costs, ratings) confirmed by code.
9. The real DWG warehouse: toilets and urinals were not in the reading (answered "cannot determine").
10. Surprise test: 9 files, 8 blind questions each; answers exist for 01-05, 07, 08 (06 skipped until the models ran
    on Modal); blind judging not run yet. Files in the session scratchpad (not in git).
11. IFC is not on the /app page yet (no picture); multi-page PDFs read page 1 only.

## Later the same night: detector e27, walls, windows

**Detector e27 is now the default** (release `v0.2-models`, `tools/get_models.py`, Modal app `drawqa-infer`).
e27 = e26l fine-tuned 15 epochs on the rebuilt set: Swiss labels without the copies the DXF stores twice (doors -15%,
windows -4% of Swiss labels), scale augmentation 0.6 instead of 0.3, whole preview sites left out.

| test (data never trained on) | e26l | e27 |
|---|---|---|
| 241 preview scans, all questions | 3676/4270 | 3694/4270 |
| ... windows | 258/482 | 272/482 |
| ... doors | 270/352 | 266/352 (5 plans fixed, 7 broken: churn) |
| ... saunas | 318/330 | 314/330 (0 fixed, 2 broken) |
| 65 Swiss PDFs read as pictures | 2300/2358 | 2310/2358 |
| ... windows | 118/130 | 124/130 |
| ... doors / sinks | 126 / 124 of 130 | 126 / 128 of 130 |

- Why windows and not doors improved: the duplicate fix mostly changed door labels, but a door labelled twice is two
  identical boxes, which teaches a detector nothing wrong; it was a counting error in the key (already corrected by
  `data/answer_corrections.jsonl`). The window gain most likely comes from the wider scale range (no ablation run).
- Remaining window errors on the preview scans: 105 of 241 plans wrong, 76 of them under the key; all 20 plans 4+
  under are `high_quality_architectural`. Checked three by hand: the key counts railing segments at a stair void as 8
  windows (11426), the glass panels of a terrace as 10 windows (13843), and splits each window into ~2 (13048). Our
  counts there are the real windows. So most of the window gap is the key, not the detector (`docs/DATASET_ISSUES.md`).
- A training run on Modal can be preempted and restarted from scratch: e27 lost 13 epochs once. `train` now saves to
  the volume every epoch and resumes an unfinished run from `last.pt`.
- Redeploying `drawqa-infer` does not replace a container that is already warm: after a redeploy, stop it
  (`modal container list`, `modal container stop --yes <id>`), or calls keep the old weights for up to 20 minutes.
- `DRAWQA_INFER_APP` picks another model service (e.g. `drawqa-infer-e27`, deployed with `DRAWQA_INFER_DETECTOR=e27`):
  test new weights without touching the default.

**Walls (layer v6-v10).** The wall model learned CubiCasa's labels, where a wall is one polygon from corner to corner
with its doors and windows inside it, so it draws walls through openings, with slanted corner cuts, ragged mask edges
and '+' crossings past outer corners. Now (`drawqa/segment.py`, used by `convert.add_outlines`):
`tidy_walls` (straight walls as clean rectangles, pieces mostly inside a surer wall dropped), `trim_to_ink` (wall ends
pulled back to the drawn ink), `merge_collinear` (one wall drawn as overlapping pieces -> one wall), `cut_openings`
(solid pieces between doors and windows; `run` = the whole wall), `wall_outline` (all walls joined, for drawing),
`wall_perimeters` (outside face and the inside face of each closed space, straight across openings; class
`wall perimeter` in the layer, cited by answers). Notes give solid wall length, length through openings, perimeters.

**Windows on big sheets.** `drawqa/repeats.py`: the detector's sure windows are used as templates for the identical
ones it skipped, kept only if the pattern along the wall matches. US dorm sheet: +16 windows, all real; 241 preview
scans: no change.

**Walls are whole walls (layer v11, agreed with the team lead).** A wall stays one wall from end to end with its doors
and windows in it, as built and as in BIM: items carry `length_m` (through the openings), `solid_length_m`, and
`openings` (kind, `along_m`, `width_m`). "Wall length" answers give the through-openings total and the solid length
in the explanation (plan 11384: 39.87 m, 33.24 m solid). The page still draws gaps at doors and windows, because a
plan is cut through them. Walls and wall perimeters are kept out of the Opus reading and merged back unchanged.

**Faster reading on /app.** The drawing is ready for questions as soon as our models have read it (4.6 s on a new
plan instead of about 2.5 minutes); Claude's full reading goes on in the background and replaces the layer when done
(171 s there). Questions asked meanwhile are answered from the models' reading; things only Claude finds (furniture)
get "cannot determine: the full reading is still in progress". `ask(..., layer=)` answers from the reading the server
holds, so a question never starts a second Claude run.

**Doors and windows below the detector's cutoff.** Window cutoff 0.40 by hand (tuned 0.45): preview 272/482 either
way, Swiss 122 vs 124/130, US dorm sheet 107 vs 92 windows. Doors and windows scored 0.15 to the cutoff go to the
Claude step as "door candidate" / "window candidate"; it confirms them on crops (the brief now says how sliding,
folding and roll-up doors are drawn) or drops them; unchecked candidates never count. Results: dorm windows 92 -> 128,
doors 200 -> 204; plan 13843 doors 24 -> 27 (key 26); 6355 21 -> 23 (key 24, two folding doors, after the brief
change); 13137, 2530, 5742 unchanged (the detector did not see those doors at all). On the dorm the full reading
found fewer other kinds of things than the run before (16 vs 30): run-to-run variation or budget spent on candidates;
not settled.

**Rare door kinds.** CubiCasa training plans: 40,424 swing doors, 731 sliding, 302 folding, 267 roll-up, 92 parallel
sliding (3% of doors, on 17% of plans). `--stage door_kinds` counts them; `DRAWQA_RFS=t` lists the images that have
them sqrt(t/f) times (repeat-factor sampling as in LVIS). e28 = e27 + 10 epochs with t = 0.5 (2.25 repeats).
